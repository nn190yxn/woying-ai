# 架构决策记录

## 使用方式

本文件记录当前代码和文档中已经形成的关键架构决策，帮助接手者理解设计取舍。状态使用：`ACTIVE`、`WATCH`、`SUPERSEDED`。

## ADR-001：采用前后端分离架构

- 状态：ACTIVE
- 决策：前端使用 Vue 3 + Vite 单页应用，后端使用 Express API 服务，所有业务接口统一挂载在 `/api` 下。
- 依据：前端需要承载大量工具表单、会员入口、Hub 页面和结果展示；后端集中处理鉴权、会员权限、AI 调用、知识库检索、持久化和支付。
- 影响：本地联调需要保持 Vite 代理目标与后端端口一致；线上由单一主站入口承载前端和 API。
- 相关文档：`ARCHITECTURE.md`、`前后端路由映射.md`、`部署运行手册.md`。

## ADR-002：统一 API 前缀为 `/api`

- 状态：ACTIVE
- 决策：后端所有主要路由挂载到 `/api/*`，前端 Axios 默认 `baseURL` 为 `/api`。
- 依据：前端开发和线上部署都需要统一入口，避免跨域和路径分散。
- 影响：新增前端请求优先复用 `frontend/src/api/request.js`；新增后端路由需要在 `backend/src/index.js` 挂载。
- 相关文档：`INTERFACES.md`、`前后端路由映射.md`。

## ADR-003：会员权限采用前端体验控制和后端接口控制双层模型

- 状态：ACTIVE
- 决策：前端通过 `membership.js` 控制入口体验，后端通过 `toolAccess.js` 和专项 `requireLevel()` 控制接口放行。
- 依据：前端需要清晰展示可用权益和升级引导；后端必须作为权限最终执行点。
- 影响：调整会员等级时要同步检查前端入口、通用工具权限、专项路由和会员页文案。
- 风险：权限配置分散，存在不同步风险。
- 相关文档：`专有概念/MembershipAndAccess.md`、`变更影响面指南.md`、`风险登记与后续治理.md`。

## ADR-004：通用工具走统一生成入口

- 状态：ACTIVE
- 决策：通用工具优先通过 `/api/generate/:toolCode` 执行，工具 code 连接前端工具目录、权限配置、知识库和测试 payload。
- 依据：通用工具数量多，统一入口便于配额、历史、权限、测试和结果协议集中处理。
- 影响：新增通用工具需要同步 `toolCatalog.js`、`toolAccess.js`、知识库映射、测试 payload 和工具页面。
- 相关文档：`模块/ToolGeneration.md`、`变更影响面指南.md`。

## ADR-005：专项工具按业务域拆分路由和页面

- 状态：ACTIVE
- 决策：抖音、小红书、私域分别使用 `douyinAgents.js`、`xhsAgents.js`、`privateAgents.js` 和对应前端目录。
- 依据：三个业务域的输入字段、诊断逻辑、会员等级和页面体验差异明显。
- 影响：专项工具可以保留领域内层结构；文档和验收要按域分别维护。
- 相关文档：`模块/DouyinBusinessLoop.md`、`模块/XhsGrowth.md`、`模块/PrivateOps.md`。

## ADR-006：抖音作为经营闭环样板链路

- 状态：ACTIVE
- 决策：抖音模块优先实现“体检 -> 15 天计划 -> 执行工具 -> 复盘 -> 洞察 -> 下一轮计划”的闭环。
- 依据：抖音链路具备本地生活老板最直接的内容、到店和投流场景，适合验证完整经营闭环。
- 影响：抖音相关改动需要额外检查计划保存、任务状态、复盘记录、洞察接口和下一轮计划上下文。
- 相关文档：`专有概念/BusinessOpsLoop.md`、`专有概念/ReviewInsights.md`、`端到端业务流程.md`。

## ADR-007：AI 输出采用结构化优先和规则兜底

- 状态：ACTIVE
- 决策：高阶生成类工具优先要求结构化 JSON 输出，同时保留 fallback 生成可渲染业务结构。
- 依据：前端页面依赖稳定字段渲染，AI 失败时仍需要给用户可理解结果。
- 影响：新增 AI 工具要同时设计结构化字段、解析清洗、fallback 和专业度测试。
- 风险：结构化输出仍可能波动，需要深测持续监控。
- 相关文档：`测试验收手册.md`、`风险登记与后续治理.md`。

## ADR-008：项目侧 LLM 配置使用 `USER_LLM_*`

- 状态：ACTIVE
- 决策：后端 AI 服务读取项目专用 `USER_LLM_API_KEY`、`USER_LLM_BASE_URL`、`USER_LLM_MODEL` 和 `AI_REQUEST_TIMEOUT`。
- 依据：项目配置应与 Agent 执行环境隔离，文档和代码只使用项目侧变量名和占位符。
- 影响：部署和排错只检查键名存在性，不记录真实值。
- 相关文档：`环境配置清单.md`、`安全与配置边界.md`。

## ADR-009：非生产环境允许 mock DB 和 mock Redis

- 状态：WATCH
- 决策：MySQL 在非生产环境不可用时切换到 `mockDb.js`，Redis 默认使用内存 mock Redis。
- 依据：本地开发和测试可降低基础设施依赖。
- 影响：新增持久化能力必须同步真实 DB 初始化和 mock DB 行为；生产环境查询失败应抛错。
- 风险：mock 行为和真实 MySQL 存在差异。
- 相关文档：`数据模型.md`、`风险登记与后续治理.md`。

## ADR-010：线上部署采用备份加最小包覆盖

- 状态：ACTIVE
- 决策：线上目录通常按运行文件管理，部署前备份目标文件，再用最小 tar 包覆盖本轮目标文件。
- 依据：线上目录通常不是 Git 仓库，必须保留可回滚路径和减少覆盖范围。
- 影响：每次发布都要记录备份路径、部署包范围、PM2 状态、健康检查和回滚命令。
- 相关文档：`部署运行手册.md`、`发布验收记录模板.md`。

## ADR-011：Wiki 放在 `.monkeycode/docs/`

- 状态：ACTIVE
- 决策：项目 Wiki、模块说明、概念说明、门禁、Runbook 和风险记录统一放在 `.monkeycode/docs/`。
- 依据：把项目协作文档和源码目录分离，同时保留与规格目录 `.monkeycode/specs/` 的关系。
- 影响：新增文档后必须更新 `INDEX.md`，并运行空白、敏感内容和索引路径校验。
- 相关文档：`Wiki 文档维护指南.md`。

## ADR-012：发布验收使用门禁和记录模板

- 状态：ACTIVE
- 决策：发布前使用 `质量门禁清单.md` 检查最低门槛，发布过程使用 `发布验收记录模板.md` 留证据。
- 依据：项目同时包含前端、后端、AI、支付、权限和线上部署，单靠 HTTP 200 无法证明交付质量。
- 影响：发布结论需要包含命令、状态、响应摘要、备份路径和风险记录。
- 相关文档：`质量门禁清单.md`、`发布验收记录模板.md`。
