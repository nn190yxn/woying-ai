# 数据治理与隐私边界

## 目标

本文档说明我赢AI中用户数据、业务数据、工具结果、日志和配置的治理边界。新增数据表、接口、日志或导出能力时，应先检查本页。

## 数据分类

| 类别 | 示例 | 主要位置 | 处理原则 |
| --- | --- | --- | --- |
| 账号身份数据 | 手机号、昵称、用户 ID、会员等级 | `users` | 最小展示，按用户隔离 |
| 认证数据 | JWT、验证码、密码哈希 | 登录、Redis、`users` | 不记录真实 token，密码只存哈希 |
| 会员与订单数据 | 套餐、订单、支付状态、会员有效期 | `orders`、`users` | 后端价格为准，回调幂等 |
| 工具输入输出 | 工具输入、AI 输出、历史结果 | `tool_results`、专项表 | 只按当前用户读取 |
| 经营诊断数据 | 诊断问卷、体检结果 | `diagnosis_reports` | 仅当前用户和授权后台可见 |
| 抖音计划数据 | 15 天计划、任务状态 | `douyin_quick_plans` | 同一用户保留最近一份 |
| 抖音复盘数据 | 执行指标、诊断、有效内容类型 | `douyin_review_records` | 多条历史，按用户隔离 |
| 行为和审计数据 | 工具执行、登录、支付、后台操作 | `analytics_events`、日志 | 记录定位字段，避免完整敏感内容 |
| 配置和密钥 | 数据库、JWT、AI、支付、SSH | 环境变量 | 文档和代码使用变量名与占位符 |

## 用户隔离原则

所有用户生成或用户专属数据必须带当前用户约束。

需要用户隔离的典型表：

- `tool_usage`
- `tool_results`
- `diagnosis_reports`
- `user_sheets`
- `douyin_quick_plans`
- `douyin_review_records`
- `user_feedbacks`

接口实现要求：

- 从 JWT 或专项 `checkAccess` 获取当前用户 ID。
- 查询条件包含 `user_id` 或等价用户约束。
- 写入时使用当前用户 ID，不信任前端传入的 `userId`。
- 更新和删除类动作必须同时约束资源 ID 和当前用户。
- 后台接口如需跨用户读取，应具备管理员权限边界。

## 密码、验证码和 token

| 数据 | 当前处理 | 边界 |
| --- | --- | --- |
| 密码 | 注册时写入 `password_hash` | 不在日志和文档中展示原文 |
| 验证码 | Redis key `code:<phone>`，有效期 300 秒 | 内测验证码只适合受控阶段 |
| JWT | 前端存入 `localStorage.token`，请求头发送 | 日志只记录用户 ID和状态 |
| `JWT_SECRET` | 环境变量 | 文档只写变量名 |

生产发布前应确认：

- `NODE_ENV=production`。
- `JWT_SECRET` 已配置且强度足够。
- `INTERNAL_TEST_VERIFICATION_CODE` 已按发布阶段处理。

## 工具输入输出治理

工具输入输出可能包含门店经营数据、投流数据、收入数据和用户自填文本。

治理要求：

- `tool_results` 只向当前用户返回。
- AI prompt 只发送完成任务所需字段。
- 日志记录输入字段名，不记录完整输入正文。
- deep:test 报告保留结构和摘要，避免真实用户数据。
- 生成结果展示应包含风险边界，避免被误解为保证性承诺。

## 经营数据治理

经营体检、作战计划和复盘数据属于用户经营数据。

关键边界：

- `diagnosis_reports` 保存用户诊断输入和分析结果。
- `douyin_quick_plans` 同一用户只保存最近一份计划。
- `douyin_review_records` 可保存多条历史复盘，用于洞察聚合。
- 复盘洞察只读取当前登录用户最近 20 条复盘。

新增经营数据能力时，需要明确：

- 数据保存频率。
- 是否保留历史版本。
- 是否可覆盖。
- 是否参与聚合。
- 是否会进入 AI prompt。
- 页面空状态和删除后的行为。

## 订单和支付数据治理

支付链路以 `backend/src/config/plans.js` 为套餐价格权威来源。

治理要求：

- 前端展示价格不能作为支付计算依据。
- 支付回调必须验签和处理幂等。
- 订单状态和会员有效期更新在同一事务中完成。
- 推荐返利失败写日志，不影响主支付事务。
- 日志记录订单 ID 和状态，不记录支付密钥或签名原文。

## 日志数据治理

日志允许记录：

- 用户 ID。
- 工具 code。
- 输入字段名。
- HTTP 路径、状态码和耗时。
- 订单 ID。
- 错误摘要。

日志避免记录：

- 完整 token。
- 真实 API Key。
- 数据库密码。
- JWT 签名值。
- 支付密钥和签名原文。
- SSH 私钥内容。
- 用户完整敏感输入。

详见 `.monkeycode/docs/日志与可观测性手册.md`。

## 配置和密钥治理

配置治理原则：

- 真实密钥只存在运行环境。
- `.env.example` 和文档使用占位符。
- 检查只记录键名存在性。
- 部署过程不打印 `.env` 真实值。
- SSH 私钥只用于连接和文件传输。

重点变量：

- `JWT_SECRET`
- `PAYMENT_CALLBACK_SECRET`
- `DB_PASSWORD` 或 `MYSQL_PASSWORD`
- `USER_LLM_API_KEY`
- `USER_LLM_BASE_URL`
- `USER_LLM_MODEL`

## AI 和知识库数据边界

AI 调用使用项目侧 `USER_LLM_*` 变量。知识库来自 `knowledge-base/` 或 `KB_ROOT_PATH` 指向目录。

治理要求：

- prompt 中只包含必要上下文。
- 知识库路径必须防止越界读取。
- 用户经营数据进入 prompt 前应确认字段必要性。
- AI 失败 fallback 不应泄露内部错误堆栈。
- 文档和日志中不写真实 AI Key。

## 后台与管理员边界

运营后台可能访问用户、订单、工具统计和反馈处理能力。

要求：

- 前端 `/admin` 路由要求登录且会员等级达到 `annual`。
- 后台接口应具备服务端权限判断。
- 后台操作写入 audit 日志。
- 后台导出或批量查看能力需要单独评估隐私风险。

## 新增数据表检查清单

新增数据表前确认：

- 是否包含 `user_id` 或清晰的归属字段。
- 是否需要唯一索引防止重复写入。
- JSON 字段是否可序列化和反序列化。
- 是否需要 `created_at` 和 `updated_at`。
- 是否已同步 `db.js` 初始化或迁移路径。
- 是否已同步 `mockDb.js` 本地行为。
- 是否已更新 `数据模型.md` 和 `核心数据流.md`。
- 是否影响备份、回滚和线上迁移。

## 新增接口检查清单

新增接口前确认：

- 是否需要登录。
- 最低会员等级是多少。
- 是否按当前用户隔离数据。
- 是否会写入工具历史或审计日志。
- 错误响应是否有 `message` 或 `error`。
- 是否会把用户数据发送给 AI。
- 是否需要在 `INTERFACES.md` 和 `前后端路由映射.md` 中登记。

## 文档和测试检查

数据治理相关改动完成后至少检查：

```bash
# 检查文档空白
git diff --check -- .monkeycode/docs

# 检查赋值型敏感内容
rg -n "(api[_-]?key|secret|password|token|JWT_SECRET|MYSQL_PASSWORD|DB_PASSWORD|USER_LLM_API_KEY)\s*[:=]\s*['\"]?[A-Za-z0-9_./+\-]{12,}" .monkeycode/docs
```

同时根据影响范围执行：

- 前端构建。
- 后端语法检查。
- 新增接口冒烟。
- 用户隔离双账号检查。
- AI 专业度深测。
