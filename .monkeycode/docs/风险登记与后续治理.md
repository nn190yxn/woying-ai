# 风险登记与后续治理

## 使用规则

风险状态使用：`OPEN`、`WATCH`、`MITIGATED`、`ACCEPTED`。

严重级别使用：`P0`、`P1`、`P2`、`P3`。

- `P0`：会导致线上不可用、数据损坏或严重安全问题。
- `P1`：会影响核心业务链路或付费用户使用。
- `P2`：影响局部功能、体验或维护效率。
- `P3`：低频问题、优化项或文档完善项。

## R-001：生成类接口耗时偏高

现象：全量深测记录中生成类工具曾出现 15 到 25 秒级请求占比，需要持续优化。

影响：用户等待时间增加，移动端体验受影响，高并发时可能拉高服务资源消耗。

当前缓解：

- `AI_REQUEST_TIMEOUT` 可配置。
- 深测报告记录耗时和专业度。
- 高阶工具已通过 JSON 结构化输出减少解析波动。

后续治理：

- 压缩 prompt 中重复说明。
- 控制 max tokens 和输出长度。
- 对长工具拆分为结构化摘要和详细内容两段。
- 在前端增加更明确的长任务 loading 反馈。

## R-002：AI 输出结构波动

现象：历史深测中出现过空结构、生成失败摘要、纯文本代替 JSON、领域内层 shape 被拍平等问题。

影响：前端页面可能无法渲染，专业度评分下降，付费工具体验受损。

当前缓解：

- `responseFormat` 支持 JSON 输出。
- `parseJsonObject()` 做轻量脏输出清洗。
- 高阶工具有 `requiresStructuredResult` 门禁。
- fallback 保证可渲染业务结构。

后续治理：

- 将结构化 schema 进一步集中管理。
- 对所有 AI 路由增加结果 shape 单元测试。
- 深测报告持续记录 `DEGRADED` 和字段缺失。

## R-003：Token Monitor 公开挂载

现象：`/api/token-monitor` 当前在后端入口直接挂载，接口可读取模型用量统计、价格参考和反馈摘要。

影响：生产环境存在运维统计暴露面。

当前缓解：

- 安全文档已标注需纳入管理员鉴权或网关控制。
- 发布门禁要求检查 Token Monitor 访问控制。

后续治理：

- 为 token monitor 路由增加管理员鉴权。
- 或在生产网关层限制来源 IP、路径或认证。
- 增加线上冒烟确认未授权访问结果。

## R-004：内容安全接口仍为基础实现

现象：`/api/security/check-text` 当前只做基础敏感词过滤，`/api/security/check-image` 当前直接返回通过。

影响：正式用户内容审核、平台合规和小程序审核场景能力不足。

当前缓解：

- 代码中保留接入微信或腾讯云内容安全 TODO。
- 安全文档已标注发布审核强相关场景需接入正式服务。

后续治理：

- 接入微信 content_check 和 img_sec_check。
- 后端保存审核结果和失败原因。
- 前端显示可理解的审核失败提示。

## R-005：内测验证码发布阶段处理

现象：`INTERNAL_TEST_VERIFICATION_CODE` 可让受控账号用固定验证码登录。

影响：正式公开发布时如果保留，会降低登录安全边界。

当前缓解：

- 部署和安全文档均要求正式公开发布前清空。
- 质量门禁和发布模板已加入检查项。

后续治理：

- 将内测验证码限定到白名单手机号。
- 增加环境检查脚本，公开发布模式下检测到该变量即失败。

## R-006：前端权限与后端权限可能不同步

现象：会员等级配置分布在前端常量、通用工具配置和专项路由中。

影响：可能出现入口显示可用但接口拒绝，或入口锁定但接口可调用。

当前缓解：

- `变更影响面指南.md` 明确同步点。
- `质量门禁清单.md` 要求多等级检查。

后续治理：

- 抽取共享权限矩阵生成前后端配置。
- 增加权限矩阵自动校验脚本。
- 对核心工具做免费、初阶、进阶、高阶四档冒烟。

## R-007：本地 mock 与线上 MySQL 行为差异

现象：非生产环境 MySQL 不可用时会使用内存 mock DB。mock DB 只覆盖常用 SQL 分支。

影响：本地测试通过的 SQL 可能在线上真实 MySQL 暴露问题，或新表忘记同步 mock。

当前缓解：

- 生产环境查询失败会抛错。
- 新持久化表要求同步 `db.js` 和 `mockDb.js`。
- 数据模型和质量门禁已记录该要求。

后续治理：

- 增加真实 MySQL 集成测试环境。
- 对新增 SQL 加最小集成测试。
- mock DB 未处理 SQL 时在测试中提升为失败。

## R-008：线上目录通常不是 Git 仓库

现象：线上部署靠打包覆盖运行文件，线上目录通常不参与 Git 工作流。

影响：需要严格控制部署包范围和回滚路径。

当前缓解：

- 部署前必须备份。
- 使用最小 tar 部署包。
- 发布模板要求记录备份包和回滚命令。

后续治理：

- 建立固定 release 包目录结构。
- 自动生成覆盖文件清单。
- 部署后自动写入验收记录。

## R-009：文档目录整体未跟踪

现象：`.monkeycode/docs/` 在当前工作区显示为未跟踪目录。

影响：文档交付依赖后续提交动作，未提交时其他协作者可能拿不到 Wiki。

当前缓解：

- 每轮新增文档后执行空白和敏感信息检查。
- 最终汇报明确未提交状态。

后续治理：

- 按项目提交策略把 `.monkeycode/docs/` 纳入版本控制。
- 提交前复查敏感信息和目录范围。

## R-010：小程序支付仍为模拟参数

现象：小程序创建订单接口当前返回模拟支付参数，代码中标注 TODO。

影响：小程序商业化支付链路还不能作为真实收款能力。

当前缓解：

- Web 支付回调主链路具备签名、幂等和会员有效期更新。
- 小程序文档标注当前状态。

后续治理：

- 接入微信支付统一下单。
- 完成支付签名、证书、回调验签和订单状态同步。
- 增加小程序支付专项验收模板。

## 风险关闭标准

风险可关闭为 `MITIGATED` 的条件：

- 已有代码、配置或流程措施消除主要影响。
- 有测试或验收记录证明措施有效。
- 文档已同步新的处理方式。
- 无需人工记忆即可按 Runbook 复现处理。

接受为 `ACCEPTED` 的条件：

- 影响范围清晰。
- 当前阶段业务接受该风险。
- 已有回滚、人工处理或监控方式。
