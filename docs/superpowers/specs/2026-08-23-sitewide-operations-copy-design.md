# 我赢AI全站运营语言体系改造设计

> 作者：Monkeycode  
> 日期：2026-08-23  
> 状态：已确认

## 1. 背景与目标

当前网站大量使用“智能体、模块、结构化诊断、系统回路、字段、接口、请求失败、版本、测试模式”等研发和产品术语。儿童素质培训机构老板虽然能看到功能，却不容易判断它与招生、到店、体验课、成交和续费的关系。

本次改造不是关键词替换，而是把网站从“AI工具展示站”调整为“儿童素质培训机构经营工作台”。所有用户可见文字优先回答：机构遇到了什么问题、问题在哪一环、本周先做什么、谁来执行、如何判断结果、何时需要顾问介入。

## 2. 已确认决策

- 第一阶段前台只聚焦儿童素质培训机构，优先适配少儿体育培训。
- 首要用户为机构老板和校长。
- 整体语气为“实战陪跑顾问”：懂招生、到店、成交和续费，结论直接、动作明确、不夸大效果。
- 改造范围覆盖客户页面、按钮、表单、提示、报告、接口错误及内部技术后台。
- 餐饮、美业等非当前行业入口从客户导航和推荐中隐藏，不删除既有代码。
- 技术术语不机械删除；必要指标首次出现时使用中文业务解释，技术配置只在受限技术设置区展示。

## 3. 双向论证与设计选择

### 3.1 支持全站统一改造

语言决定产品定位。继续使用“智能体矩阵”和技术模块，会让客户把产品理解为复杂AI工具箱，而不是能帮助校区招生和经营的陪跑服务。统一行业语言能够降低理解门槛，强化“软件＋陪跑服务”定位，并让页面落到可执行动作。

### 3.2 反对机械批量替换

同一词语在不同业务环节含义不同。例如“转化”可能指咨询转预约、预约转到店或体验转报名；“客户”可能指家长或学员家庭。少儿体育也不能照搬学科培训的成绩和知识点话术。因此必须按角色、场景和页面任务重写，而不是全局查找替换。

### 3.3 采用方案

采用“按经营流程重构语言体系”：

> 找问题 → 定本周目标 → 执行招生动作 → 跟进家长 → 提高到店和报名 → 查看结果 → 顾问复盘

保留现有业务能力和接口兼容性，优先调整信息架构、公共文案源和用户可见文字。

## 4. 全站语言主线

所有页面围绕六个问题组织：

1. 校区现在遇到了什么经营问题；
2. 问题主要出在哪个招生环节；
3. 本周最应该先改什么；
4. 由谁在什么时候完成；
5. 完成后登记什么结果；
6. 应该继续、调整、停止还是找顾问。

### 4.1 优先使用的行业对象

- 机构、校区、课程、体验课、课包；
- 校长、课程顾问、老师、教练；
- 家长、孩子、学员；
- 咨询、邀约、到店、体验、报名；
- 消课、续费、转介绍；
- 本周行动、完成标准、经营结果、顾问建议。

### 4.2 客户页面原则上不展示

- 智能体矩阵、模块编号、结构化协议、系统回路；
- 增强回路、调节回路、前端能力、页面版本；
- Mock、API Key、Redis、未知模块、请求失败；
- 没有解释的英文状态和指标缩写。

## 5. 页面与导航设计

### 5.1 首页和老板工作台

从展示工具数量改为展示：本周招生目标、当前主要问题、今日行动、待跟进家长和体验课、咨询到报名变化、顾问提醒。

示例：

- “AI获客智能体矩阵”改为“本周招生行动”；
- “进入结构化诊断”改为“看看招生问题出在哪”；
- “生成行动方案”改为“制定本周行动”。

### 5.2 经营诊断

删除阶段和模块编号，改为五个业务步骤：

1. 了解校区和主推课程；
2. 填写本周招生数据；
3. 找出最影响结果的一环；
4. 确定本周优先动作；
5. 七天后回来复盘。

结果统一展示：主要问题、判断依据、可能原因、最多两个本周动作、暂不建议做的事、观察指标、停止或顾问介入条件。

### 5.3 抖音招生

围绕真实工作组织：选择主推课程、确定家长问题、安排拍摄、准备口播与镜头、发布前检查、登记播放与咨询、判断真正带来家长咨询的内容。

不承诺自动精准获客或快速见效，统一说明建议基于机构填写信息，需要连续执行和记录结果。

### 5.4 家长跟进与成交

按家长状态组织：新咨询、待联系、待邀约、已约体验、体验前提醒、体验后回访、已报名、暂未报名、即将续费、可邀请老带新。

### 5.5 数据与计算工具

主标题改为老板的问题：

- CAC：招一个新生花多少钱；
- LTV：一名学员在读期间能带来多少收入；
- 场地利用率：场地有没有充分排课；
- 人效：每位老师带来多少收入；
- 盈亏平衡：每月招多少新生才能保本；
- 转化漏斗：家长在哪一步没有继续。

专业缩写可放在解释中，不作为首次使用的主标题。

### 5.6 会员与陪跑服务

不按工具数量、生成次数和模块数量销售，按经营成果与陪跑深度组织：基础经营工具、7天招生行动、15天陪跑、顾问审核与纠偏、阶段经营复盘、定制经营支持。明确区分系统建议和真人顾问服务。

### 5.7 内部后台

分为：机构运营、陪跑交付、客户服务、财务管理、技术设置。

技术设置保留准确术语并补充中文解释，同时满足：密钥默认隐藏；日志不展示手机号、Token和完整用户输入；非技术角色不可见；Mock只显示为“测试数据模式”。

### 5.8 其他行业入口

餐饮、美业等能力从客户导航、首页推荐和工具目录隐藏。首阶段前台只呈现儿童素质培训业务，不删除底层代码和历史数据。

## 6. 统一文案规范

### 6.1 页面结构

每个页面依次说明：这是做什么的、需要填写什么、为什么这样判断、接下来做什么。禁止先介绍技术实现。

### 6.2 标题

标题使用经营问题或具体动作，例如“看看招生问题出在哪”“跟进待到店家长”“回看这7天有没有改善”。不使用“智能体矩阵、结构化诊断、增长模型、多维能力分析、模块中心”。

### 6.3 按钮

按钮描述点击后的具体结果：

- 提交 → 提交本周数据；
- 生成 → 生成本周行动；
- 开始诊断 → 看看问题出在哪；
- 保存快照 → 保存本周期结果；
- 创建计划 → 制定7天行动；
- 运行复盘 → 回看这7天的结果；
- 加载历史 → 查看以前的记录；
- 导出CSV → 下载经营记录。

### 6.4 表单

每个指标解释业务口径。空数据不称为字段缺失，提示“这项暂时没有数据也可以继续，但判断结果会标记为需要核实”。表单只收集必要的经营聚合数据，不引导录入儿童姓名、手机号等个人信息。

### 6.5 诊断结果

固定结构为：当前最需要解决的问题、判断依据、可能原因、本周先做、暂时不要做、观察结果、停止或求助条件。数据不足和无真实模型配置时明确显示“需要顾问确认”。

### 6.6 系统状态与错误

- 加载中 → 正在打开以前的经营记录；
- 处理中 → 正在整理本周问题和行动建议；
- 请求失败 → 暂时没能完成，请稍后再试；
- 权限不足 → 当前账号不能查看，请联系机构管理员；
- 数据为空 → 还没有记录，从本周第一次填写开始；
- needs_review → 需要顾问确认；
- pending / processing / completed / failed → 待开始 / 进行中 / 已完成 / 未完成，请检查原因。

后端错误必须映射为用户动作语境，不能把堆栈、数据库错误或内部状态原样返回普通用户。

### 6.7 AI与顾问边界

推荐使用“根据你填写的信息整理”“给出参考建议”“需要顾问确认”“连续记录后再判断”。禁止“精准诊断、自动获客、快速见效、最优方案、保证提升、一键解决招生问题”等不可验证承诺。

## 7. 角色化语言

- 校长：经营问题、优先级、负责人、结果和是否需要顾问；
- 课程顾问：新咨询、邀约、到店提醒、体验后回访、报名和未报名原因；
- 老师/教练：课堂表现、训练进步、课后反馈、剩余课时和续费配合；
- 陪跑顾问：机构执行进度、待审核内容、纠偏建议和周期前后对比；
- 客服/财务：问题处理、订单、退款、对账；
- 技术管理员：接口、模型、数据服务和脱敏日志，仅在受限区域使用技术术语。

## 8. 实施顺序

1. 建立全站运营语言词典和禁用词规则；
2. 改造导航、路由、工具目录、公共按钮、表格、错误状态等公共源头；
3. 重写首页、诊断、获客、7天行动、复盘、家长跟进、续费、会员等核心页面；
4. 治理内部后台及技术配置的角色隔离和敏感信息；
5. 处理计算器、表格模板、小红书、私域、后端返回文案和AI结果模板等长尾内容。

每阶段完成后单独验收，避免一次性机械替换造成语义错误。

## 9. 验收标准

1. 普通用户页面不出现模块编号、页面版本、Mock、API Key、Redis、未知模块等内部文字；
2. 核心页面明确使用校区、课程、家长、体验课、到店、报名、续费等行业对象；
3. 每个主要页面都有明确下一步，按钮不使用含义模糊的“执行、处理、生成”；
4. 不同角色只看到与其工作相关的语言和信息；
5. 必要经营指标首次出现有中文业务解释；
6. 系统建议、规则判断、真实模型和顾问确认的边界明确，不伪造AI能力；
7. 通过全站静态文案扫描、敏感技术词扫描、前端生产构建和后端回归测试；
8. 抽查桌面、平板和手机页面，确认文案变长后无溢出、遮挡或按钮错位；
9. 餐饮、美业入口不在首阶段客户前台出现，但既有代码、接口和历史数据不被删除。

## 10. 边界与风险

- 用户可见文字还可能来自后端、数据库历史内容、AI输出和第三方服务，不能只扫描Vue模板；
- 少儿体育使用知识库的语言结构，但不直接照搬学科培训的成绩提升案例；
- ROI、消课率、续费率等专业指标不能一刀切删除，应使用中文解释；
- 技术后台改文案时必须同步检查角色权限、密钥遮罩和日志脱敏；
- 本次不改业务计算逻辑、不删除多行业代码、不迁移线上数据、不部署。
