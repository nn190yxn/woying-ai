# 全量工具专业度深度测试方案

## 使用规则

- 每个 Agent 执行前必须先读取本文件和 `docs/线上验收执行记录.md`。
- 逐工具测试，每测完一个工具必须立即更新本文档对应行的测试状态。
- 状态只使用：`PENDING`、`PASS`、`FAIL`、`SKIP`。
- 严禁输出 API Key、数据库密码、JWT_SECRET 或 `.env` 真实值。
- 测试输入使用固定标准 payload，不使用随机或边界极端值（边界测试单独规划）。
- 所有测试在 `NODE_ENV=production` 环境下执行，必须携带有效 JWT token。
- 任一工具 `FAIL` 时记录原因，不停止后续工具测试（与验收验收不同，此处允许单工具失败继续）。
- 测试结束后汇总通过率、失败清单和需要修复的工具列表。

## 测试环境

| 项 | 值 |
|---|---|
| 本机后端 | `http://127.0.0.1:3000` |
| 公网入口 | `http://124.223.3.175` |
| 后端目录 | `/home/ubuntu/woying-ai/backend` |
| PM2 服务 | `woying-backend` |
| JWT 签 token | `node scripts/smoke-core-endpoints.js` 内置签发，读取 `.env` 的 `JWT_SECRET` |
| 超时 | 单接口 60 秒 |

## 执行方式

所有测试通过 `npm run smoke:core` 的基础框架执行，但需要逐工具单独调用以获取完整输出结构。

统一鉴权：使用线上 `.env` 的 `JWT_SECRET` 签 token，`userId=1, memberLevel=annual`。

## 专业度评估维度

每个工具按 6 个维度评分，每维度 0-2 分，总分 0-12：

| 维度 | 0分 | 1分 | 2分 |
|---|---|---|---|
| 行业基准 | 无任何对标数据 | 有1-2项对标但不完整 | 有完整行业区间/阈值/城市等级 |
| 行动建议 | 无 actions 或只有笼统建议 | 有 actions 但缺 owner/timeline | 有具体可执行 actions 含 priority/owner/timeline |
| 风险提示 | 无 riskNotes | 有风险提示但只覆盖1项 | 覆盖适用边界+统计口径+城市差异+复核要求 |
| 知识库引用 | 无 KB 引用 | kbEnhanced=true 但文件少 | kbEnhanced=true 且命中行业专项KB |
| 结构深度 | 单层列表或纯文本 | 有2-3层分节但有空洞 | 多层分节+诊断/拆分/对标+完整结构 |
| 会员引导 | 无 CTA | 有 CTA 但文案笼统 | 有具体升级场景引导 |

通过标准：总分 >= 8 为 PASS，< 8 为 FAIL。

### 小红书工具返回结构差异

**发现内容**：小红书 17 个工具存在两种返回结构：

   - 符合当前验收标准中的预期输出结构
   - 前端可直接消费统一字段

2. **旧版 result 嵌套**（A1, A4, A5, A14）：
   - 返回 `{"agent":"...","result":{"radar":[...],"totalScore":...,"diagnosis":"...","suggestions":[...]}}`

**判断**：
- A1 的 result 结构有行业价值（雷达图五维诊断），但前端需要单独适配
- 如果前端当前已适配这种结构，可以保留
- 如果前端期望统一 schema，需要评估迁移成本
- 建议：记录为"结构差异"而非"缺陷"，由前端确认消费方式后再决定是否统一

### 2026-05-14 全局审查补充结论

#### 1. 小红书、抖音、私域的长期架构判断

- 小红书、抖音、私域属于高阶经营功能，长期主链路应统一为“知识库检索 + AI 生成 + 结构化解析 + fallback”的 Knowledge-AI 执行能力。
- 统一 Knowledge-AI 执行能力是长期最合适的方向，原因是三类专项都依赖行业知识、平台规则、用户上下文和动态策略生成，纯规则知识库难以覆盖完整业务场景。
- 统一引擎不等于立刻统一所有响应字段。前端当前大量页面直接消费领域结构，短中期需要保留领域适配层或双结构兼容。
- 推荐分层：底层统一 AI 执行、检索、fallback、日志、meta；上层保留各领域专用 payload，例如诊断雷达、定价矩阵、90 天计划、会员分层、裂变模型。

#### 2. 前端消费结构审查

- 小红书 `frontend/src/views/xhs/GenericAgent.vue` 直接消费 `summary/sections/actions/riskNotes` 等接近统一结构字段。
- 小红书 `AccountDiagnosisAgent.vue` 直接消费 `response.result.radar/totalScore/level/diagnosis/suggestions`。
- 抖音多个专项页面仍使用本地模拟或页面专用结构，`DiagnosisAgent.vue` 当前本地生成 `radar/diagnosis/suggestions`，部分页面直接消费 `data.result` 的专用字段。
- 私域页面普遍调用 `/api/private/*` 并直接消费 `data.result`，字段包括 `radar/avgScore/kpis/recommendedTiers/phases/retentionCalendar/scriptSnippets` 等。
- 结论：后端直接把小红书、抖音、私域全部改成单一 `summary/sections/actions` 会带来前端断裂风险。迁移时应先新增兼容包装，保留 `result` 内的领域字段，同时在外层补齐统一 schema 字段。

#### 3. 计算器深度测试 payload 与输入协议不匹配

- 对 `backend/scripts/test-payloads-g.json`、`test-payloads-h.json`、`test-payloads-i.json`、`test-payloads-j.json` 与 `backend/src/services/calculatorEngine.js` 的 `CALCULATORS[*].inputs` 做只读对比后，发现大量 FAIL 来自 payload 字段名不匹配。
- G 组中 G1-G6、G11-G12 与引擎输入匹配；G7-G10、G13-G15 存在字段不匹配。
- H 组中 H5、H6、H9、H11 与引擎输入匹配；其余工具存在字段不匹配。
- I 组中 I5、I10、I12、I20 与引擎输入匹配；其余工具存在字段不匹配。
- J 组当前 9 个测试 payload 全部与引擎输入存在字段不匹配。
- 结论：G/H/I/J 的 generic-fallback 或低分结果不能直接判定为业务未实现。第一步应修正测试 payload 或在后端输入归一层增加别名兼容，再重新跑深度测试。

#### 4. 修复优先级建议

- P0：修正深度测试 payload 与 `CALCULATORS` 输入协议，或在 `generate.js`/`calculatorEngine.js` 前置归一层补字段别名，重新确认真实 FAIL 清单。
- P1：为小红书、抖音、私域建立 Knowledge-AI 共享执行层，统一 KB 检索、AI 调用、fallback、日志、meta，同时保留领域结果结构。
- P2：在各专项路由外层补 `status/degraded/summary/sections/actions/riskNotes/meta/customizationCTA`，内部继续保留 `result` 专用字段，前端逐页迁移。
- P3：RAG 工具优化 prompt 和 JSON parser，要求 AI 稳定返回 actions、riskNotes、benchmarks、recommendedTools。
