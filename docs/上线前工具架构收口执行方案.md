# 上线前工具架构收口执行方案

## 1. 文档定位

本文档是给后续执行 Agent（Kimi2.6）使用的严格执行方案。

本轮任务目标是完成上线前最后一次结构性收口，避免后续继续出现“工具入口分散、返回结构不统一、测试误判、专项页面断裂”的问题。

本轮任务不是重新设计产品，也不是大规模重写工具业务逻辑。

## 2. 核心判断

小红书、抖音、私域属于高阶功能，长期必须走“知识库 + AI”主链路。知识库只提供事实、规则、案例和行业语料，AI 负责根据用户输入生成个性化策略、诊断、方案和行动计划。

本轮收口的正确方向是：

- 底层执行能力统一：知识库检索、AI 调用、prompt 组装、结构化解析、fallback、日志、meta、权限。
- 上层业务表达保留：小红书账号诊断、抖音雷达图、私域会员体系、裂变模型、90 天计划等领域结构。

因此，本轮不应把所有工具强行改成完全相同的业务字段。正确目标是统一外层协议，保留内层领域结构。

## 3. 最终交付标准

本轮完成后，应达到以下状态：

- 所有工具入口可追踪：每个工具明确走哪个路由、哪个 engine、哪个前端页面。
- 所有后端工具具备统一外层协议：`status/degraded/summary/sections/actions/riskNotes/meta/customizationCTA`。
- 小红书、抖音、私域高阶工具具备共享 Knowledge-AI 执行层或明确兼容层设计。
- 专项工具继续保留 `result` 内的领域专用字段，前端页面不因结构收口而断裂。
- 深度测试 payload 与真实输入协议一致，测试先校验输入协议，再评价专业度。
- 文档明确后续新增工具规则，避免再长出新的路由体系或结果协议。

## 4. 禁止事项

执行期间必须遵守以下限制：

- 禁止读取、打印、展示 `.env`、API Key、JWT_SECRET、数据库密码、支付密钥或私钥真实值。
- 禁止提交 `WOYING.pem`、真实 `.env`、`backend/env.server-fill.template`、`audit-freeze/`。
- 禁止执行删除类命令，例如 `rm`、`git rm`、`git clean`、`docker system prune`。
- 禁止执行 `npm audit fix --force`。
- 禁止在线上直接盲改业务代码。
- 禁止把小红书、抖音、私域降级成纯模板或纯规则知识库。
- 禁止直接移除前端正在消费的 `result` 领域字段。
- 禁止只凭 deep-test 低分判断工具未实现；必须先核对输入协议。
- 禁止一次性重构全站页面展示；本轮只做架构收口和兼容。
- 禁止引入第二套新的工具执行体系。

## 6. 当前已知事实

### 6.1 主链路状态

- `/api/generate/:toolCode` 通过 `generate.js`、`engineRegistry.js` 执行。
- `engineRegistry.js` 已有 `rag/template/score/diagnosis/calculator/spreadsheet` 等 engine。
- `resultSchema.js` 已提供 `createToolResult()`，统一外层字段。
- `buildUnifiedResponse()` 当前位于 `engineRegistry.js`。

### 6.2 小红书状态

- `xhsAgents.js` 是独立路由。
- `GenericAgent.vue` 消费 `summary/sections/actions/riskNotes` 等接近统一结构字段。
- `AccountDiagnosisAgent.vue` 消费 `response.result.radar/totalScore/level/diagnosis/suggestions`。
- 小红书当前部分工具接近统一结构，部分保留旧结构。

### 6.3 抖音状态

- `douyinAgents.js` 是独立路由。
- 后端部分抖音工具已恢复“知识库 + AI”主链路。
- 前端多个 `douyin/*.vue` 页面使用页面专用字段。
- `DiagnosisAgent.vue` 当前仍在前端本地生成 `radar/diagnosis/suggestions`。

### 6.4 私域状态

- `privateAgents.js` 是独立路由。
- 私域页面大量调用 `/api/private/*` 并消费 `data.result`。
- 典型字段包括 `radar/avgScore/kpis/recommendedTiers/phases/retentionCalendar/scriptSnippets`。

### 6.5 计算器测试状态

G/H/I/J 组存在大量测试 payload 与 `calculatorEngine.js` 输入协议不匹配。

已知匹配情况：

- G 组：G1-G6、G11-G12 匹配；G7-G10、G13-G15 不匹配。
- H 组：H5、H6、H9、H11 匹配；其余不匹配。
- I 组：I5、I10、I12、I20 匹配；其余不匹配。
- J 组：当前 9 个测试 payload 全部不匹配。

因此，G/H/I/J 当前低分不能直接等同于工具未实现。

### 阶段 2：计算器测试输入协议修正

目标：先消除测试误判，确保 deep-test 使用真实输入协议。

执行动作：

- 对比 `backend/scripts/test-payloads-g.json`、`test-payloads-h.json`、`test-payloads-i.json`、`test-payloads-j.json` 与 `CALCULATORS[*].inputs`。
- 优先修测试 payload，使字段名与 `CALCULATORS` 一致。
- 如果前端真实提交字段和 `CALCULATORS` 不一致，再考虑在 `generate.js` 或 calculator 前置归一层增加字段别名。
- 修改后运行只读对比脚本，确认缺失字段归零或有明确例外说明。

推荐校验脚本：

```bash
node --input-type=module - <<'NODE'
import { CALCULATORS } from './backend/src/services/calculatorEngine.js';
import fs from 'node:fs';
const files = ['g','h','i','j'].map(x => `./backend/scripts/test-payloads-${x}.json`);
for (const file of files) {
  const rows = JSON.parse(fs.readFileSync(file, 'utf8'));
  console.log(`\n${file}`);
  for (const row of rows) {
    const code = row.endpoint.split('/').pop();
    const calc = CALCULATORS[code];
    if (!calc) {
      console.log(`${row.code} ${code}: NO_CALCULATOR`);
      continue;
    }
    const keys = Object.keys(row.payload || {});
    const missing = (calc.inputs || []).filter(k => !(k in row.payload));
    const extra = keys.filter(k => !(calc.inputs || []).includes(k));
    const status = missing.length ? 'MISMATCH' : 'OK';
    console.log(`${row.code} ${code}: ${status} missing=[${missing.join(',')}] extra=[${extra.join(',')}]`);
  }
}
NODE
```

验收标准：

- G/H/I/J 测试 payload 的 `missing` 字段全部清零，或每个例外都有文档说明。
- 重新运行 G/H/I/J 深度测试。
- 更新 `docs/全量工具专业度深度测试方案.md` 中计算器真实 PASS/FAIL 状态。

### 阶段 3：统一外层协议兼容层

目标：不破坏现有前端页面的前提下，让所有专项路由拥有统一外层字段。

执行动作：

- 新增或复用统一包装函数，推荐放在 `backend/src/services/resultSchema.js`。
- 包装函数必须支持保留领域 `result`。
- 对 `xhsAgents.js`、`douyinAgents.js`、`privateAgents.js` 逐个路由加外层包装。
- 保留原有 `result` 字段和所有前端正在消费的领域字段。
- 不改变业务计算逻辑。

推荐函数形态：

```javascript
export function createDomainToolResult(domainResult = {}, options = {}) {
  return createToolResult({
    summary: options.summary || domainResult.summary || domainResult.diagnosis || '',
    sections: options.sections || domainResult.sections || [],
    actions: options.actions || domainResult.actions || [],
    riskNotes: options.riskNotes || domainResult.riskNotes || [],
    benchmarks: options.benchmarks || domainResult.benchmarks || null,
    extra: {
      result: domainResult
    },
    meta: {
      ...(domainResult.meta || {}),
      ...(options.meta || {})
    }
  }, options)
}
```

注意：上述代码是建议形态，执行时必须结合现有 `createToolResult()` 的保留键逻辑检查，避免 `result` 被过滤。

验收标准：

- 原有前端依赖的 `data.result` 仍存在。

- `customizationCTA` 不丢失。

### 阶段 4：Knowledge-AI 共享执行层设计与最小接入

目标：把高阶专项的 AI 能力统一到共享执行层，避免每个路由重复维护 AI、KB、fallback、日志。

执行动作：

- 优先新增共享服务，不急于迁移所有工具。
- 推荐新建 `backend/src/services/knowledgeAiEngine.js`，或在 `engineRegistry.js` 注册 `knowledge-ai` engine。
- 共享层职责：
  - 获取 KB context。
  - 构造 system/user prompt。
  - 调用 `generateStructured()`。
  - 解析 JSON。
  - fallback 到领域模板。
  - 返回统一外层 + 领域内层。
  - 写入 `meta.engineType=knowledge-ai`、`meta.kbEnhanced`、`meta.aiUsed`、`meta.kbFilesUsed` 等。
- 先选择 1 个低风险工具试点，例如小红书 `quick-start-plan` 或抖音 `full-strategy`。
- 试点通过后再决定是否批量迁移。

验收标准：

- 试点工具 AI 可用时 `degraded=false`。
- AI 不可用时 fallback 可用，且 `degraded=true`。

## 10. 风险控制

### 10.1 前端断裂风险

风险：后端统一结构后，前端页面找不到 `data.result` 或领域字段。

控制：保留 `result` 内层字段。先补外层，后迁移前端。

### 10.2 AI 降级风险

风险：AI 超时、403、401、JSON 解析失败导致高阶工具降级。

控制：保留 fallback，并在 `meta` 中明确 `aiUsed/degraded/fallbackType`。

### 10.3 测试误判风险

风险：payload 字段不匹配导致业务工具被误判 FAIL。

控制：deep-test 先做输入协议校验，输入不匹配标记为 `INPUT_MISMATCH`。

### 10.4 重构过度风险

风险：为统一而重写大量专项页面和业务逻辑。

控制：本轮只做外层协议、共享执行能力和测试口径收口。

### 10.5 文档漂移风险

风险：代码改完后文档未更新，后续 Agent 再次误判。

控制：每阶段必须同步更新文档，最终验收包含文档检查。

## 11. 退出标准

满足以下条件，才能认为本轮结构性收口完成：

- `generate` 主链路、计算器、小红书、抖音、私域都有明确入口归属。
- 小红书、抖音、私域代表端点具备统一外层协议。
- 小红书、抖音、私域代表端点保留前端需要的 `result` 领域字段。
- G/H/I/J 测试 payload 与真实输入协议完成对齐或完成例外记录。
- `smoke:core` 通过。
- 后端关键文件 `node --check` 通过。
- 前端 `npm run build` 通过。
- 深度测试结果不再把输入协议错误误判成业务失败。
- 文档已记录后续新增工具规则。

## 12. 交付后允许的修改范围

本轮完成后，后续上线前修改应限制在以下范围：

- 单个工具 prompt 优化。
- 单个工具公式、阈值、文案优化。
- 单个前端页面展示优化。
- 单个接口 bug 修复。
- 单个工具测试 payload 补充。
- AI 超时、fallback、日志等稳定性优化。

后续应避免以下结构性动作：

- 新增独立工具执行体系。
- 新增独立结果协议。
- 绕过统一外层协议。
- 把高阶 AI 工具降级成纯规则模板。
- 大面积重写专项页面。

## 13. 给执行 Agent 的最终要求

执行时按阶段推进。每完成一个阶段，必须：

- 更新 todo 状态。
- 运行该阶段要求的测试。
- 把测试结果写入文档。
- 发现异常时停止进入下一阶段。
- 对不确定的结构性决策先向用户确认。

本轮目标是上线前最后一次结构性调整。质量优先于速度，兼容优先于激进统一，验证优先于主观判断。
